x402とは、HTTPステータスコード402（Payment Required）を使ってAPIやコンテンツへのアクセスをオンチェーン決済と結びつけるプロトコルのことです。vet402は、そのx402決済が実際に履行されるかどうかを第三者として買って検証する独立検証機関で、私はこれを個人で開発・運用しています。402は「決済が必要」を意味するステータスコードですが、この記事はその402が決済とは無関係の理由で全URLから返ってきた朝の話です。

## 起：06:24、全部が402になった

2026-09-23 06:24 JST、外形監視のログに `health http 402` という一行が並びました。vet402.com のトップページも、APIのヘルスチェックエンドポイントも、静的アセットまで含めて全部が402です。決済ゲートを実装しているプロダクトなので、最初に疑ったのは自分のミドルウェアでした。デプロイのタイミングが悪かったか、環境変数が飛んだか、Next.jsのルーティングでどこかのハンドラが全部にマッチしてしまったか。ローカルで再現しようとしても再現しません。curlでレスポンスボディを見ても、それらしいエラーメッセージは出てきません。402の中身は、決済要求のJSONではなく、ほぼ空でした。ここで「自分のコードのどこかがおかしい」という前提のまま調べ続けると詰みます。実際、この日はここで15分ほど自分のミドルウェアのコードを読み返していました。

## 承：見るべきはボディではなくヘッダだった

突破口はレスポンスヘッダです。`x-vercel-error` を見ると `DEPLOYMENT_DISABLED` と入っていました。これは自分のアプリケーションコードが返したエラーではなく、Vercel側がデプロイメントそのものを無効化しているサインです。つまり402はNext.jsのミドルウェアが決めたものではなく、ホスト側が「このデプロイは配信しない」と決めた結果として、リクエストがアプリケーションに届く前に返されていたわけです。

ここでVercelのAPIを叩いてチームの状態を確認すると、`softBlock` というフィールドが立っていました。原因は fluidCpuDuration の fair use 超過です。Vercelのプランには公正利用のしきい値があり、チーム単位の使用量がそれを超えると、個々のプロジェクトの設定を触らなくてもデプロイが止められます。自分のコードは何一つ変わっていないのに、チーム全体の使用量が理由で全プロジェクトが同時に止まってしまいます。これは一つのURLだけを追いかけていても、なかなか見つけられない種類の障害でした。

この切り分けを機械化したのが `check_vercel_team` 関数です。Vercel CLIが保存しているトークンを読んで、チームの `billing.plan` と `softBlock` を確認します。

```bash
check_vercel_team() {
  local auth="$HOME/Library/Application Support/com.vercel.cli/auth.json"
  [[ -f "$auth" ]] || return 0
  local token
  token=$(python3 -c 'import json,sys;print(json.load(open(sys.argv[1])).get("token",""))' "$auth" 2>/dev/null) || return 0
  [[ -n "$token" ]] || return 0
  local body
  body=$(curl -sL --max-time 20 -H "Authorization: Bearer $token" https://api.vercel.com/v2/teams/gokaku 2>/dev/null) || return 0
```

使用量APIそのものは時間範囲の指定で `invalid_time_range` を3形式試して全部弾かれたので諦めました。読めるのはチームの状態、つまりプランが落ちていないか、softBlockが立っていないかの2点だけです。402が出てから気づくのでは遅いので、402が出る前にこの2点だけ先に鳴らす設計にしました。

## 転：監視が「原因の場所」を教えていなかった

ここが本題です。外形監視は正常に「落ちている」ことを検知していました。しかし警告文が `health http 402` としか書いていなかったので、人間が読んでも「決済ゲートがおかしいのか」「自分のNext.jsのミドルウェアがおかしいのか」の判断がつきません。監視が動いていることと、監視が原因の場所を教えてくれることは別問題だと痛感しました。

さらに監査で分かったのは、FAILマーカーの読み手が `daily-improvement-loop` というタスクだけで、そのタスクが無効化されていたことです。実測で30分ごとに938行分、1ヶ月近く鳴り続けていたのに誰にも届いていませんでした。鳴っていることと、届いていることも別問題です。

修正は2段構えにしました。1つ目は、状態がOKからFAILに変わった最初の1回と、以後6時間（21600秒）ごとにだけ、`state/ALERTS.md` に直接書き込むようにしたことです。連投を避けつつ、確実に人が読むファイルに書きます。

```bash
if (( last == 0 || now - last >= REALERT_SECONDS )); then
  rea
```

そして2つ目は、こちらが本質的な修正です。警告文にVercelチームの状態を混ぜ込みました。

```bash
if [[ -n "$TEAM_NOTE" ]]; then
  printf '[%s] %s\n' "$ts" "$TEAM_NOTE" >>"$LOG"
  note_alert "$TEAM_NOTE — Vercel のチーム状態。プランか停止状態が変わった。課金ページ: https://vercel.com/gokaku/~/settings/billing"
fi
```

「402が出ている」ではなく「VercelのチームがsoftBlockされている、課金ページはここ」まで警告文に書くことで、次に同じことが起きたときは読んだ瞬間に原因の場所へ辿り着けます。監視の役目は「異常を検知すること」ではなく「人間が次に見る場所を1秒で言い当てること」だと考え直しました。

もう一つの判断は cron の本数を減らしたことです。もともと複数のcronジョブが個別にヘルスチェックを叩いており、fluidCpuDurationの消費源の一つになっていました。launchd（`com.kizuna.vouch-uptime-monitor`）で動かす外形監視を1本に絞り、無駄な重複呼び出しを削りました。この期間は支出上限を設けない運用にしていたので、上限がない以上は止まる前に気づける値を毎回読みにいく設計にする、という判断とセットでした。

## 結

この一件で確認できたのは、決済プロトコルを検証する立場である以上、決済失敗と決済とは無関係な失敗を人間が数秒で区別できる状態にしておかないと、検証機関としての信頼性そのものが揺らぐということです。だからvet402の監視は、ステータスコードだけを見て鳴くのではなく、ヘッダとホスト側APIの状態まで遡って「原因の場所」を警告文に書き込むところまでを一つの機能として設計しています。
