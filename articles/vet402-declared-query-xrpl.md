x402とは、HTTPの402 Payment Requiredステータスコードを使って、APIの呼び出しごとに支払いを要求するプロトコルのことです。売り手は402応答のボディやヘッダに支払い条件（チャレンジ）を載せ、買い手はそれに従って支払いを完了させてから同じリソースに再アクセスします。vet402は、この一連のやり取りが仕様通りに成立するかを買い手として実際に検証する仕組みです。今回はXRPL上のエンドポイントを検証していて、支払いを済ませたはずなのに400が続けて返ってくるという場面にぶつかりました。

## 起：支払いは通っているのに400が続く

検証対象はXRPL向けのAPIで、402チャレンジに従って支払いを送り、トランザクションも台帳に取り込まれていました。それなのに再アクセスのたびに400が返ってきます。最初に疑ったのは当然、売り手側の実装です。支払い確認のロジックにバグがあるのか、検証ハッシュの照合に失敗しているのか、ログを見てもエラーメッセージは「invalid query」の一点張りで、手がかりはほとんど残っていませんでした。XRPLのトランザクション自体は正しく処理されているのに、リソース側が400を返す理由が見当たりませんでした。

ここで数時間、売り手実装の推測に時間を使ってしまいました。しかし落ち着いて402のボディを読み返すと、答えはそこに書かれていました。

## 転：402は「取得したいクエリ名」を宣言していた

売り手の402応答には、単に支払い条件だけでなく「このリソースにアクセスする際はこのクエリパラメータ名を使ってください」という宣言が含まれていました。つまりURLに掲載されている素のリソースURLに対して、402ドキュメントが指定するクエリ名を自分で足してからリクエストする必要があったわけです。こちらはそれをせず、掲載URLそのままにリクエストしていたので、売り手から見れば「必須パラメータが無い不正なクエリ」として400を返していた、というだけでした。400の山は相手のバグではなく、こちらが402の宣言を読み飛ばしていたことが原因でした。

この気づきを受けて、Issue #29として「L1の支払い付き要求の本文とクエリを、売り手の402の宣言から取る」実装に着手しました。2026-09-17に着手し、2026-09-20に最初の実装を入れています。設計の核は、parseChallengeが支払い条件を取り出したのと同じ文書から、宣言されたクエリ名や本文の要素を取るという点です。チャレンジのヘッダとボディのどちらを採用するかで解釈がずれると、取得した宣言内容と実際に支払い条件として検証した文書が食い違うバグを生みかねません。

```ts
function challengeDocument(input: { bodyText: string; headers: Headers }): unknown {
  const headerB64 = input.headers.get("PAYMENT-REQUIRED");
  if (headerB64) {
    const headerOnly = parseChallenge({ bodyText: "", headers: input.headers });
    if (headerOnly) {
      try {
        return JSON.parse(Buffer.from(headerB64, "base64").toString("utf8"));
      } catch {
        return undefined;
      }
    }
  }
  if (input.bodyText && parseChallenge({ bodyText: input.bodyText, headers: new Headers() })) {
    return parseJson(input.bodyText);
  }
  return undefined;
}
```

ここでやっているのは「parseChallengeが採用した文書」をもう一度同じ優先順位で選び直すことだけです。ヘッダのPAYMENT-REQUIREDをbase64デコードしてJSONにできればそれを使い、できなければボディのJSONを使います。宣言されたクエリ名を取り出すロジックとチャレンジの解釈ロジックを別の関数に分けると、どちらか片方だけ仕様変更したときにずれる恐れがあったため、同じ関数を経由させる形にしました。

実際の宣言抽出とURL衝突の判定は declaredRequestBodyFromDoc / declaredRequestUrlFromDoc という別ファイルの規則本体に任せています。declared-input.ts 側はあくまで「どの文書を見るか」を決めるだけの薄い層にして、2026-09-29のタイミングで規則本体と分離しました。

```ts
export function declaredRequestUrl(input: { resourceUrl: string; bodyText: string; headers: Headers }): DeclaredRequestUrl {
  return declaredRequestUrlFromDoc({ resourceUrl: input.resourceUrl, document: challengeDocument(input) });
}
```

掲載URLに既に同名のクエリパラメータがある場合は、宣言された名前で上書きするのではなく、既存の値を尊重して宣言側を無視する扱いにしています。売り手が掲載URLに十分な情報を既に埋め込んでいるケースと、402で追加の宣言を出すケースが混在するため、衝突時に機械的に上書きすると売り手の意図と逆の挙動になりかねないからです。

## 許可リストをCAIP-2でXRPLだけに絞った理由

この「宣言された入力を自動で足す」仕組みは、便利な反面リスクもあります。チェーンによってクエリの意味合いやアドレス形式が大きく異なるため、XRPL以外のチェーンでも同じ規則を無条件に適用すると、意図しないパラメータを他チェーンのエンドポイントに送りつけてしまう恐れがあります。そこで許可リストはCAIP-2のチェーンID形式で管理し、XRPLのチェーンIDだけを対象に限定しました。他のチェーンに対応を広げる際は、個別に検証してから許可リストに追加する運用にしています。網羅的に対応範囲を広げるより、検証済みの範囲だけを正としたほうが、何かを「検証した」と言う以上は誠実だと考えています。

## 行にdeclared / empty / refusedを残す

この仕組みを入れてから、ログの一行一行に declared（宣言を適用した）、empty（宣言が無かった）、refused（衝突で宣言を無視した）のいずれかの状態を残すようにしました。デバッグのその場しのぎではなく、後からまとめて数えられることを目的にしています。何件のエンドポイントで宣言があり、何件で衝突が起きているかを一覧できれば、x402の実装がどれくらい「宣言付きクエリ」のパターンを使っているかの実態も見えてきます。

## 結

最初の declared 行が200で成立するのを確認できたとき、山のような400の正体がようやく腑に落ちました。相手の実装を疑うよりも先に、自分が402の宣言を正しく読めているかをまず疑うようにしています。この順番を徹底したことが、vet402を「売り手の仕様を推測で補う検証機」ではなく「売り手が明示した契約をそのまま検証する機」として作る、という設計の軸になっています。
