## ステーブルコイン決済パイロットとは

ステーブルコイン決済パイロットとは、USDCやUSDT、JPYCなどの法定通貨連動型トークンを使って、実際の請求・入金業務の一部を本番相当のフローで試験運用することです。多くのチームは「送金がオンチェーンで成功するか」を検証すればパイロットは十分だと考えがちですが、実務で必要になるのはその先です。私はステーブルコイン入金消込ツールSoroiを作る中で、送金の成否とは別に詰まった箇所が6つありました。今回はそれを実装ベースで振り返ります。

## 1. 承認権限の設計

APIキーによる認証は「動くかどうか」より「失敗時にどちらへ倒すか」の設計で詰まりました。Soroiの`lib/apiAuth.ts`では、Supabase未接続時をfail-closed（503）にしています。

```ts
if (!isApiServiceConfigured()) {
  return { ok: false, status: 503, errorCode: "supabase_not_configured" };
}
```

無効キーで即401を返すのも意図的な判断です。無効キーでレート制限テーブルに行を作らせると、でたらめなトークンの連投でテーブルが肥大化してしまうため、キー検証を先に行い、有効キーだけをレート制限判定に回すようにしています。さらにレート制限のRPC自体が失敗した場合もfail-open（素通し）にせず拒否するようにしました。承認権限は「通す条件」より「落とす条件」を先に決めるほうが実装が安定すると感じています。

## 2. 入金元と請求データの紐付け

送金が成功しても、それが誰からの入金なのかは別の問題です。Soroiでは取引先アドレス帳（`counterparties`/`counterparty_addresses`）を使い、既知アドレスからの入金にconfidenceを加点する仕組みにしています。

```ts
export const KNOWN_ADDRESS_BONUS = 0.15;

function addressBookKey(counterpartyName: string, address: string): string {
  return `${counterpartyName.trim()} ${address.trim().toLowerCase()}`;
}
```

ここは加点方式にしたのがポイントです。金額一致（配点0.6）と時期一致（配点0.4）という既存のゲート条件を壊さずに、独立した証拠として上乗せする設計にしたことで、既存の照合結果を消さずに、複数候補が競合したときだけ既知アドレス側を優先できるようになりました。DB読み出しはサービス層（`matchService.ts`）が担い、`matching.ts`側は引数で受け取るだけの純関数に保っています。これは、この紐付けロジックをnode --testで単体検証したかったためです。

## 3. 対象取引の適格性判定

通貨が違う入金を請求書に紐付けてしまうミスは、監査ラウンド2で実際に見つかった穴でした。自動照合側にはガードがあったのに、手動照合側（`createManualMatch`）に同じチェックが欠けていたのです。

```ts
export function currenciesMatch(
  invoiceCurrency: Currency,
  transactionTokenSymbol: Currency
): boolean {
  return invoiceCurrency === transactionTokenSymbol;
}
```

この関数を自動照合・手動照合の両方から共有する形に直したことで、判定ロジックの重複と乖離を防いでいます。適格性判定は「一箇所に書いたつもり」が一番危険で、経路が増えるたびに同じチェックを漏れなく通す設計が必要になります。

## 4. ファイナリティの扱い

Soroiの照合ロジック自体はブロック確定を待つかどうかを直接扱いませんが、`blockTimestamp`をもとに時期一致を判定するため、いつの時点のタイムスタンプを信頼するかは設計判断が必要でした。チェーンによってファイナリティの速さは違うため、確定前のトランザクションを早期に照合対象へ入れてしまうと、リオーグが起きたときに消込が巻き戻る可能性があります。そこで取得層（`getTransactions`）でファイナリティ済みのものだけを渡す前提を置き、照合エンジン側はその前提の上で金額と時期だけを純粋に見る、という役割分担にしました。

## 5. 例外処理

自動照合を全件即確定にすると危険なケースがあります。未知アドレスや類似アドレスからの入金は、`needsReview`フラグを立てて自動確定させず「要確認」に留めるようにしています。

```ts
export interface MatchResult {
  invoiceId: string;
  transactionId: string;
  matchRule: MatchRule;
  confidence: number;
  needsReview?: boolean;
  reviewReason?: MatchReviewReason;
}
```

confidenceはあくまで突合の確からしさを表すものであり、会計上の正しさを示すものではありません。これは税理士法52条を意識した設計判断で、UIの文言でも「税務判断を示唆しない」という線を守る必要がありました。例外処理は機能そのものというより、機能に線引きを引く作業だと感じています。

## 6. 最終的な消込

最後は`matches`テーブルへのINSERTです。ここは同時実行と再割当ての防止が課題でした。

```ts
// - 既にアクティブ照合がある請求書/トランザクションは候補から除外（再割当てしない）。
// - 却下済みの (invoice, tx) ペアは再提案しない。
// - UNIQUE(transaction_id, invoice_id) との衝突は ignoreDuplicates で無害化
//   （同時実行・二重呼び出しへの安全弁）。
```

さらに0009マイグレーションで「1請求書/1入金につきアクティブ照合1件」という部分UNIQUEインデックスを追加しています。これは一括upsertでは検出できないため、1行ずつupsertを行い、その候補だけをスキップする実装にしました。消込は「照合ロジックが正しい」だけでは終わらず、DB制約とアプリ側の挙動が食い違わないところまで詰めて初めて安定すると実感しています。

## まとめ

送金の成否はパイロットの入り口に過ぎません。承認権限、入金元の紐付け、適格性判定、ファイナリティ、例外処理、消込という6項目は、どれも実データが増えたときに壊れやすい箇所でした。Soroiではこれらを純関数の照合エンジンとサービス層に分けて実装することで、node --testでロジックを検証しつつ、実Supabase接続時の挙動は別レイヤーで確認できる構成にしています。パイロットを設計する際の参考になれば幸いです。
