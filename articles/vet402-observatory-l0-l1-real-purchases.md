稼働初日、x402 のカタログを Neon（Postgres）へ流し込んだら、insert が例外で止まりました。原因は `description` に紛れていた NUL バイトです。同じ時期に、本番の公開ページが空になり、USDC を送るウォレットが MetaMask と別のアドレスになっていました。

作っていたのは vet402 です。x402（HTTP 402 を使う決済の仕組み）で公開されている有料エンドポイントを、買わずに全部見て回る層（L0）と、実際に USDC を払って届くかを確かめる層（L1）に分けて動かしています。この記事は 2026年8月に書いた事故の記録を、9月22日時点の数字に直したものです。

## カタログの大きさ

Coinbase Developer Platform（CDP）が公開している Bazaar のカタログは認証なしで読めます。

```
GET https://api.cdp.coinbase.com/platform/v2/x402/discovery/resources?limit=100&offset=N
```

2026年9月22日 9時07分（JST）に `pagination.total` を取ると 15,230 件でした。

## なぜ L0 と L1 を分けたか

カタログのエンドポイントを片っ端から GET で叩いて、402 が返らなければ死んでいると判定する。これをやると誤判定が量産されます。2026年9月22日時点でカタログの先頭100件を見ると、GET が 83 件、POST が 17 件でした。POST 宣言のものを GET で叩けば、生きていても落ちて見えます。

救いは、カタログ側が `extensions.bazaar.info.input.method` に HTTP メソッドを書いてくれていることでした。推測せず、この宣言をそのまま使う。宣言がない項目は「未検証」のラベルを付けて止める。L0 の中身はほぼこれだけです。

L0 は買わないので $0 で回ります。記録するのは、生きているか、圏外になったか、という事実だけ。実際に払う L1 とはテーブルもルートも分けました。1万件を超えるカタログを毎日全部買って確かめたら、USDC がいくらあっても足りません。L0 で価格やレスポンスの形、`quality.l30DaysUniquePayers` のような「実際に払われているか」の手がかりを見て、L1 に回す数を絞ります。

## L1 の支払いに、コードで予算の上限を持たせた

L1 は本物の USDC を送ります。いちばん怖かったのは、バグで同じエンドポイントに何百回も払ってしまうことでした。

1日の予算上限は、環境変数でも設定ファイルでもなく、支払いを組み立てる直前のコードに置きました。cron が起動するたびに、その日の送金の合計を DB から集計し、上限を超えていたら支払いのリクエストそのものを作りません。送ったあとにログで気づくのでは遅いので、送る前に必ず通る一本道にしました。

ただ、この「集計してから判断する」形には穴がありました。2本の実行が同時に集計すると、両方とも上限の内側に見えて、両方とも払えてしまいます。今は、支払いの前に予算を1文の SQL で予約する形に変えています。上限を超える予約はその1文の中で弾かれるので、同時に走っても合計は上限を超えません。予算のロジックは新しいファイルに閉じ込め、L0 側の `src/lib/scoring/*` と `src/lib/chain/*` には触れていません。

## 事故1: カタログの取り込みで NUL バイトが混ざって落ちた

CDP から取った JSON を Drizzle 経由でそのまま Neon に書いたところ、`description` に `\u0000` を含む項目があり、insert が例外を出して止まりました。Postgres の text 型は NUL バイトを受け付けません。外のAPIの返事を信じてそのまま書けば、いつかは踏む問題でした。

直したのは、取り込みの文字列フィールド全部に `replace(/\u0000/g, '')` をかける関数を1枚挟んだことだけです。ただ、それを取り込みの最初の関門に固定したので、あとからフィールドを足しても同じ道を通るようになりました。

## 事故2: .vercelignore の誤マッチで公開ページが消えた

L0 の観測結果は DB に書くほか、スナップショットを `state/` に JSON で書き出して静的に読む経路もありました。デプロイ後、`/observatory` が本番だけ空になりました。

原因は `.vercelignore` に書いていた除外パターンです。`state` を含むパスに広く当たってしまい、ビルドが参照するファイルまで弾いていました。ローカルのビルドでは `.vercelignore` が効かないので再現しません。Vercel の上でだけ壊れる種類の事故です。

除外パターンは `/state/` のようにルート直下だけに絞りました。それ以来、除外パターンを足すときは実際のパス一覧に当てて空打ちしてから入れています。ローカルと本番でビルド結果がずれるのは、だいたいこの手のファイルのせいでした。

## 事故3: 秘密鍵の 0x の有無で MetaMask と食い違った

L1 のウォレットの秘密鍵を環境変数に入れるとき、MetaMask の「秘密鍵をエクスポート」でコピーした文字列には `0x` が付いていませんでした。一方、Node.js でウォレットを復元するライブラリの多くは `0x` 付きを前提にしています。

厄介だったのは、`0x` なしで渡しても復元が通ってしまい、MetaMask とは違うアドレスができたことです。エラーで落ちてくれれば気づけました。実際には、残高ゼロのアドレスに向けて「送金成功」のログだけが出る状態に一瞬なりました。

環境変数を読む箇所で、先頭に `0x` がなければ付ける処理を1か所にまとめ、どの経路で鍵を受け取っても必ずそこを通すようにしました。

```
// MetaMaskエクスポート値の形
// 例: 4c0883a69102937d6231471b5dbb6...（0xなし）
// ライブラリが期待する形
// 例: 0x4c0883a69102937d6231471b5dbb6...
```

## その後

この記事を最初に書いた8月、L1 が払っていたのは Base の上だけでした。2026年9月22日時点で vet402.com のトップページ「5. Chains」を見ると、決済済みの購入の記録は Base 3,780 件、Solana 82 件、Tempo 28 件、XRPL 2 件、Arc 2 件です。Tempo だけは x402 ではなく MPP 経由で、XRPL は RLUSD で払っています。

## 3つの事故を振り返って

どれも、外から来た文字列をそのまま信じた箇所で壊れていました。カタログの JSON、デプロイ設定のパターン、秘密鍵の書き方です。L0 と L1 を分けて、実際の支払いを予算上限の内側に閉じ込めていたので、壊れても被害はテーブル1つ、cron 1本の範囲で止まりました。

チェーンが増えたぶん、入口も増えています。正規化の漏れはまたどこかで出ると思っています。取り込み、デプロイ、鍵、それぞれの入口に1枚挟む。これは変えずに続けます。
