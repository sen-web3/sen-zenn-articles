# x402の公開カタログ15,092件を、実際に買って検証するパイプラインを作った話

Vouchとは、x402プロトコルに対応した決済エンドポイントの公開カタログを対象に、購入せずに全数を観測する層（L0）と、実際にUSDCで購入して決済履行を検証する層（L1）を分離して運用する検証パイプラインのことです。x402はHTTPステータスコード402を使った決済プロトコルで、Coinbase Developer Platform（CDP）のFacilitatorが公開しているBazaarカタログには2026年8月時点で1万5千件規模のエンドポイントが登録されています。この記事では、そのカタログを取り込んで検証パイプラインとして稼働させるまでに実際に踏んだ事故と、その直し方を書きます。

## なぜL0とL1を分けたか

x402の検証で一番やってはいけないのは、「カタログに載っているエンドポイントを片っ端からGETで叩いて、402が返らなかったら死んでいると判定する」ことです。CDPのBazaar discoveryのレスポンスを実際に取得して先頭100件のメソッド分布を見ると、GETが72件、POSTが28件でした。3割弱がPOST宣言のエンドポイントで、これをGET一律でプローブすると誤判定をそのまま量産してしまいます。x402リポジトリ側にもこの手の型誤判定の教訓があり、回避策はカタログ自体が`extensions.bazaar.info.input.method`としてHTTPメソッドを宣言してくれている点にありました。推測せず、宣言をそのまま使う。宣言がない項目は「未検証」ラベルで止める。これがL0の核です。

L0は無購買・$0で回る全数観測層と決めました。役割は「生きているか/圏外化したか」を事実として記録するだけで、実際に決済を通す検証（L1）とは物理的に別テーブル・別ルートに分離しています。理由は単純で、1万5千件を毎日実購買で検証したらUSDCがいくらあっても足りないからです。L0で価格・レスポンス形状・`quality.l30DaysUniquePayers`のような実需兆候を観測し、そのうえでL1に回す母数を絞り込む設計にしました。

Bazaar discoveryのAPIは認証不要で、`pagination.total`が実測で14988件、`limit=100`固定なので全数取得は150リクエストで済みます。1日1回のバッチなら十分に余裕があります。

```
GET https://api.cdp.coinbase.com/platform/v2/x402/discovery/resources?limit=100&offset=N
```

## L1のUSDC決済に予算上限をコードで持たせる

L1はBase mainnet上で実際にUSDCを送る層なので、ここで一番怖いのは「バグって同じエンドポイントに何百回も課金する」事故です。1日あたりの予算上限は環境変数や設定ファイルではなく、決済を発行する直前のコードパスに埋め込みました。cronジョブが起動するたびにその日の累計送金額をDBから集計し、上限を超えていたらそもそも決済リクエストを組み立てない、という順序です。上限チェックを「送金後にログを見て気づく」運用にせず、「送金前に必ず通る一本道」に置いたのがポイントです。これはL0側の`src/lib/scoring/*`・`src/lib/chain/*`には一切触れない設計とも整合していて、L1の予算ロジックは新規ファイルに閉じ込め、既存のスコアリングロジックと物理的に別ファイルで並走できるようにしています。

## 事故1: カタログ取り込みでNULバイトが混入して落ちた

稼働初日、Bazaar discoveryから取得したJSONをそのままDrizzle経由でNeon（Postgres）に流し込んだところ、`description`フィールドの中に`\u0000`（NULバイト）を含む項目が混ざっていて、insertが例外を吐いて止まりました。Postgresのtext型はNULバイトを許容しないため、外部APIのレスポンスをそのまま信用して書き込むと必ずどこかで踏む問題です。直し方は、取り込みバッチの文字列フィールドすべてに対して`replace(/\u0000/g, '')`をかけるサニタイズ関数を一枚噛ませただけですが、この一枚を「取り込み処理の最初の関門」として固定したことで、以降のフィールド追加でも同じ経路を通るようにしました。

## 事故2: .vercelignoreのstateディレクトリ誤マッチで公開ページが消えた

L0の観測結果はDBに書くだけでなく、スナップショットを`state/`ディレクトリにJSONで吐き出して静的に参照する経路も持たせていました。ところがデプロイ後に`/observatory`のページが本番だけ空になる現象が発生し、原因は`.vercelignore`に書いていた汎用的な除外パターンが`state`という語を含むパスに広く誤マッチし、ビルド成果物側の参照ファイルまで一緒に弾いていたことでした。ローカルビルドでは`.vercelignore`が効かないため再現せず、Vercel上のデプロイでだけ発生する類の事故です。直し方は、除外パターンを`/state/`のようにルート直下の該当ディレクトリだけに絞る形へ書き換え、デプロイごとにビルドログの「除外されたファイル一覧」を目視で確認する手順を挟むことにしました。ignoreファイルの誤マッチは、ローカルとリモートでビルド結果が食い違う典型パターンなので、以降は新しい除外パターンを足すたびに実際のパス一覧に対してドライランする癖をつけています。

## 事故3: 秘密鍵の0xプレフィックス有無でMetaMaskと食い違った

L1でBase mainnetにUSDCを送るウォレットの秘密鍵を環境変数に設定する際、MetaMaskの「秘密鍵をエクスポート」機能でコピーした文字列には`0x`プレフィックスが付いていませんでした。一方でNode.js側でウォレットを復元するライブラリの多くは`0x`プレフィックス付きの文字列を前提にしていて、プレフィックスなしのまま渡すと復元自体は通ってしまうのに、生成されるアドレスがMetaMask上のアドレスと一致しないという厄介な壊れ方をしました。エラーで落ちてくれれば気づけますが、静かに別アドレスを生成してしまうため、テスト送金で残高がゼロのアドレスに向かって「送金成功」のログだけが出るという状態に一瞬なりました。直し方は環境変数を読み込む箇所で先頭に`0x`が無ければ付与する正規化を一箇所に集約し、以降はどの経路で秘密鍵を受け取っても同じ関数を必ず通す形にしています。

```
// MetaMaskエクスポート値の形
// 例: 4c0883a69102937d6231471b5dbb6...（0xなし）
// ライブラリが期待する形
// 例: 0x4c0883a69102937d6231471b5dbb6...
```

## まとめ

3つの事故に共通していたのは、外部から来た文字列（カタログのJSON、デプロイ設定のパターン、秘密鍵の表記）を無条件に信用した箇所で必ず壊れる、という点でした。L0とL1を分離してBase mainnetの実購買を予算上限つきで囲ったことで、事故が起きても被害範囲がDrizzleのテーブル単位・cronジョブ単位に閉じ、初日のうちに全部直せたのは設計として機能したと感じています。1万5千件規模のカタログを相手にする以上、こうした一箇所の正規化漏れは今後も出てくるはずなので、取り込み・デプロイ・鍵管理それぞれの入口に必ず一枚サニタイズを挟む、という原則は崩さずに運用を続けています。
