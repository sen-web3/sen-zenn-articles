私は複数のWebプロダクトを個人で開発・運用しています。実装・デプロイ・計測の大部分をClaude Codeなどのコーディングエージェントに任せる体制で、私が書くコードより、エージェントが書くコードの方が圧倒的に多い状態が半年以上続いています。

その運用の中で、あるパターンの事故が繰り返し起きました。**エージェントが「完了しました」「確認済みです」と報告してくるのに、外の世界では何も起きていない、あるいは壊れたままになっている**、というものです。

今回はその実例と、規律で止めようとして失敗した経緯、最終的に道具で止めた話を書きます。最後に、この問題に私がどう名前を付けているかと、いま作っているものの話を少しだけします。

## 実例: 同じ日に4回、同じ構造の誤報が出た

2026年8月のある日、エージェントからの報告に同じ構造の誤りが1日で4回出ました。どれも「隣にあるものを測って、本物だと言う」誤りです。

**1. リダイレクトの手前を測る。** 「ページは正常に配信されています」という報告の根拠が、`curl` を `-L` なしで叩いた結果でした。見ていたのはリダイレクト前の応答で、転送先の本体は一度も見ていませんでした。測ってはいる。ただし対象の隣を。

**2. 単位を読み違える。** アクセス解析の events 数を「訪問者数」として報告してきました。イベント数と人数は別の指標で、片方だけ取れば数字は実際より大きく見えます。数字自体は本物なので、報告だけ読むと疑う理由がありません。

**3. APIの成功レスポンスを「実在」と呼ぶ。** 外部サービスへの投稿処理で、APIが成功を返したことを根拠に「投稿されています」と報告してきました。実際に相手側の画面を見に行くと、投稿は存在しませんでした。「リクエストが受理された」と「相手側に残った」は別の事実です。

**4. 沈黙の欠落。** データ検査のスクリプトが「全件クリーン」と報告してきましたが、パーサが途中の4行を例外も出さずに読み飛ばしていました。検査は正しく走った。ただし欠けた母集団に対して。

どの回も、エージェントは嘘をつこうとしていたわけではないと思います。**検証らしき行為を実行し、その結果を誠実に報告している。ただ、測っている対象が本物ではなかった。** そして報告文面だけからは、それを見分ける方法がありません。

もっと長く潜伏した例もあります。あるサービスでは、デプロイ済みコントラクトとABIの不一致で機能が約30日間、全リクエストで失敗し続けていました。エラーを外に出さないfail-closed設計だったため上位層からは正常と区別が付かず、ヘルスチェックはその間ずっと `"ok"` を返していました。「エラーが出ない壊れ方」は、完了報告の正しさを前提にした運用では検出できません。

## 規律では止まらなかった

最初に試したのは規律です。「完了と主張する前に検証コマンドを実行し、その出力を確認せよ」という指示をエージェントの行動規範に組み込みました。世の中にも同種のプロンプト規律は流通していて、考え方自体は正しいと思います。

しかし私の環境では、これで事故は止まりませんでした。理由は振り返ると単純で、**規律は「検証を実行させる」ことはできても、「検証が対象を測れているか」を保証しない**からです。上の4例は全て、エージェント本人の主観では検証済みでした。`-L` なしの `curl` も、events の取得も、APIレスポンスの確認も、「検証コマンドの実行」ではあるのです。

もうひとつ、実行主体と採点主体が同じであることの構造的な限界もあります。エージェント自身にpre-commitフックを回避された報告（`--no-verify` 問題）はAnthropic公式リポジトリのissueにもあります。

https://github.com/anthropics/claude-code/issues/40117

検証層をエージェント本体の内側に置く限り、検証そのものが作業の一部として最適化・省略の対象になります。

## 道具にした

規律で3回失敗した後、やり方を変えました。**エージェントの外側に、決め打ちの実測プローブを置く**方法です。

自作したのは小さなスクリプトで、やることは地味です。

- URLを渡すと、リダイレクトを**追った先**のステータス・Content-Type・実バイト数・ファイル種別判定まで返す。「手前を測る」ことが構造的にできない
- アクセス解析はeventsとvisitorsを**必ず両方**返す。片方だけ取って人数と呼ぶことができない
- 外部サービスへの操作は「APIが成功したか」ではなく「**相手側に何が残っているか**」を取得して確認する

ポイントは、賢いことを一切していない点です。LLMに判定させず、決定的なコマンドで外部の実状態を測って、エージェントの主張と突き合わせるだけ。それでも、冒頭の4類型はこのプローブを通した時点で全て機械的に捕捉できるようになりました。判断をよくするのではなく、**誤った測り方を選べないように道具の側で塞ぐ**方が、私の環境では効きました。

## うちだけの問題ではなかった

この現象、計測した研究があります。

**arXiv:2606.09863「From Confident Closing to Silent Failure: Characterizing False Success in LLM Agents」**（2026年6月）は、tau2-benchの9,876軌跡・8モデル系列で、単一制御ドメインの**false success率45〜48%**（モデル別では13〜79%）、自己評価アーキテクチャのAppWorld 1,879軌跡では**75.8%**という数字を報告しています。つまり「タスクを完了したと主張したが実際には失敗していた」割合が、条件次第で半分前後に達するということです。同論文の推奨は、LLMに判定させるのではなく「lightweight, domain-calibrated detectors」を本番監視に使うこと。私が自作プローブで辿り着いた結論と同じ方向でした。

https://arxiv.org/html/2606.09863

事故としてもっとも知られているのは2025年7月のReplit事件だと思います。コードフリーズ中のAIエージェントが本番データベースを削除し、その後**偽データ4,000件の生成と単体テスト結果の虚偽報告でそれを隠した**という当事者報告で、Hacker Newsで143ポイント付きました。

https://news.ycombinator.com/item?id=44625119

Claude Code公式リポジトリには、リアクション3,286件・コメント583件（2026年8月時点）の品質劣化の大規模スレッドがあり（主題は品質劣化全般で、虚偽の完了報告はその一部です）、個別issueにも「作ったと主張したセーフガードが実は作られていなかった」「Edit失敗が黙殺され壊れたコードが本番へ」といった報告が並びます。

https://github.com/anthropics/claude-code/issues/42796

日本語圏でも、「完了しました」の直後にスクリプトが動いていなかった経験から50行のStop hookを自作した方の記事があります。発想は私の自作プローブと同型です。

https://qiita.com/yurukusa/items/d89abeea354ba9ef95f2

Stack Overflowの2025年開発者調査では、AI出力の精度を「積極的に不信」とする回答が46%で、「信頼」の33%を上回りました。不信は既に多数派です。ただ、その不信に対応する**道具のカテゴリには、まだ名前が付いていない**と感じています。

## この問題の名前:「完了主張の事後監査」

私はこれを「**完了主張の事後監査**」と呼ぶことにしました。英語で書くなら post-hoc auditing of completion claims です。

前提はひとつだけです。**エージェントの「完了しました」は、事実ではなく主張である。** 主張は、主張した本人の提出物（ログ・トレース・自己申告）ではなく、外部の実状態——デプロイ先の実応答、DBの実レコード、API相手側に残った状態——で監査する。実行の前に守るガードレールでも、出力の品質を採点するevalsでもなく、**事後に、外側から、決定的に**測るという層です。

既存のLLM評価・観測ツール（トレース収集・LLM-as-a-judge・ガードレール系）は私も調べて回りましたが、私が調べた範囲では、判定材料はどれも「エージェントが出したもの」でした。エージェントの主張の外側を独立に測って突合する層は、少なくとも私が必要とした形では見つからず、だから自作しました。

## 正直な線引き: 50行の自作で足りる範囲

先に、**作らなくていい人**の話をします。

一人で1〜2製品を回していて、成果物がリポジトリの中で完結しているなら、たぶん自作フックで足ります。具体的には次の範囲は無料・小規模な自作が現にカバーしています。

- 完了語と実行痕跡のテキスト照合（前述のQiita記事が50行で実装済み）
- 「検証コマンドを打て」という規律のプロンプト注入
- リポ内のテスト結果・diffを根拠にした、実装者と検証者の分離
- CI上の決定的チェック（lint・テスト・シークレットスキャン）

HTTP応答をひとつ見る程度なら、フックの延長で書けます。この範囲の人を引き込むつもりはありません。まず50行から始めるのが正しいと思います。

自作の外に残るのは、私の実感では次の4つです。

1. **外部実状態のプローブ集**: リダイレクト・Content-Type・実バイト数・単位の取り違えといった「測り方の罠」を、罠ごと吸収した状態で保守され続けるもの。罠は踏むたびに増えます
2. **履歴**: エージェント別・タスク別に「主張と実測が食い違った率」を蓄積したもの。1回の検証は自作できても、傾向は蓄積がないと見えません
3. **横断ダッシュボードと共有**: 製品やリポを跨いだ突合結果を1箇所で見る・チームや監査に見せる層
4. **保守**: 私が調べた同型OSSはスター1〜123の個人メンテでした。検証層は、それ自体が黙って壊れると全てが崩れる場所です

## 作っているもの

この「完了主張の事後監査」を、Claude Code / Agent SDKのフックに差し込むハーネスとして作っています。エージェントが完了を主張した時点で外部実状態のプローブが走り、主張と実測の突合結果が履歴として残る、という形です。

まだ設計段階で、コードを見せられる状態ではありません。同じ問題で困っている方がどれくらいいるのかを先に知りたいので、関心があれば待機リストに登録してもらえると助かります。登録時に「何に一番困っているか」を1問だけ聞いています。それが設計の順番を決めます。

https://completion-audit.netlify.app/?utm_source=sen_zenn&utm_medium=cta&utm_campaign=completion-audit

自作フックで足りている方は、そのままで大丈夫です。その線引きより向こうで困っている方の話を聞かせてください。
