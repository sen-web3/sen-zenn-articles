抽出器（extractor）とは、公開されているランディングページやドキュメントの文章から「daily」「always」「100%」のような断定語を機械的に拾い出し、実際の稼働実績と突き合わせるための下地を作るコードのことです。vet402はx402決済プロトコルの履行を実際に購入して検証する独立検証機関として、こうした公開面の断定と実測の乖離を数える仕組みを内部に持っています。この記事は、その抽出器のコメント判定が壊れていた話と、直した過程についてのものです。

## 事故の経緯

2026-08-13から09-02にかけて、あるLPが"probed daily"と書いていたのに、同じサイトの/observatory/stateというエンドポイントは実測18.8%しか出していませんでした。この乖離が20日間残ったのは、公開面の断定語を誰も機械で数えていなかったからです。src/lib/claims/extract.tsは、この「数える側」を作るためのコードです。

抽出器自体はシンプルで、ASSERTIVE_TERMSという断定語のリストと正規表現を持ち、公開コピーからマッチする箇所を拾います。ただし対象は英語の散文だけに絞る必要があります。コード識別子（Promise.allやrows.every）、コメント、import、classNameのような非散文属性まで拾ってしまうと、ノイズだらけになってしまいます。そのためNON_PROSE_KEYSという属性名のリストを用意し、値ごと空白に潰す処理を入れています。空白に潰すのは文字を削除すると行番号がずれてしまうためで、blank関数は改行だけ残して同じ長さの空白に置き換えます。

## 直前1文字だけを見ていた判定

問題はコメント判定の実装にありました。2026-09-23まで、コメントの範囲はスラッシュの直前1文字だけを見て「ここはコメントの開きか」を決めていました。旧opensCommentという手書きの関数です。この規則の下では、JSXの本文中に書かれた散文の`(/*)`という文字列を、コメントの開きだと誤読してしまいます。すると次に現れる本物の`*/`までの範囲がまるごと空白に潰されてしまいます。

実測した数字がこちらです。methodologyという公開ページの本文に`(/*)`を1つ挿入しただけで、検出される断定語の数が41から14まで落ちました。27件分の主張が、コメントだと誤認されて消えていたことになります。この抽出器を守っていたのはtests/claims-registry.test.tsに置かれたDETECTION_FLOORという下限値のテストだけで、穴そのものは塞がっていませんでした。テストは壊れた挙動が壊れたままであることを固定していただけで、直っているかどうかは何も保証していなかったわけです。

## TypeScript自身に聞く

修正の方針は、コメント判定を手書きの規則に任せず、TypeScriptコンパイラ自身に聞くことにしました。コミット29d527fで、stripComments関数をts.createSourceFileベースの実装に置き換えています。

```ts
export function stripComments(src: string): string {
  const sf = ts.createSourceFile("surface.tsx", src, ts.ScriptTarget.Latest, true, ts.ScriptKind.TSX);
  const out = src.split("");
  const seen = new Set<number>();

  const blank = (pos: number, end: number) => {
    for (let i = pos; i < end && i < out.length; i++) if (out[i] !== "\n") out[i] = " ";
  };
```

ポイントはts.ScriptKind.TSXでソースファイルを作っていることです。公開コピーの本文はReactコンポーネントのJSXとして書かれていることが多く、拡張子はtsxです。TSXとして構文解析させると、JSXTextノードの中に現れる`/*`という文字列はテキストの一部としてそのまま扱われ、コメントとしては認識されません。コメントはトークンに付随するtriviaとして、各トークンの直前にleadingCommentRangesという形で位置情報が返ってきます。

つまり「ここからここまでがコメントだ」という判断を、こちらで文字を1つずつ読んで推測する必要がなくなります。パーサーが構文木を作る過程で確定させた範囲を、そのまま取得するだけで済みます。ts.getLeadingCommentRangesにソースコード全体とトークンの開始位置を渡すと、そのトークンの前に付いているコメントの範囲（複数ありうる）を配列で返してくれます。この範囲だけをblankで空白に潰せば、JSXの本文にある散文の`(/*)`は一切触られません。同じ位置を二重に潰さないようseenでトークン開始位置を記録しているのも、AST走査を素直にやると同じコメント範囲を複数回踏むことがあるためです。

## 数字で確認する

置き換え後に同じ注入テストをやり直すと、検出数は43から44になりました。挿入した`(/*)`自体には断定語が含まれていないので、素朴には検出数は変わらないはずですが、抽出器が文単位でtermをカウントする実装のため、挿入によって文の区切りが1つ増えたぶんの差分が出ています。この程度の差分は説明がつくもので、少なくとも「コメントだと誤認して27件消える」という壊れ方は完全に消えました。

## テストの書き換え

旧DETECTION_FLOORは「41件以上検出できていること」を固定していたので、41から14に落ちても、下限を14未満まで下げない限りテストは失敗しません。下限そのものが壊れた挙動に合わせて緩く設定されていて、事故を検出できない構造になっていました。node:testで書き直したテストでは、`(/*)`を含むmethodologyの断定語数が挿入前後で変わらないこと、あるいは説明可能な差分の範囲に収まることを直接固定するアサーションに変えています。

```ts
// tests/claims-registry.test.ts（意図の抜粋）
// 旧: assert(count >= DETECTION_FLOOR)  // 41→14でも通ってしまう
// 新: assert.equal(before, after, "prose /* must not be read as comment open")
```

壊れた挙動を固定するテストは、壊れたままであることを証明するだけで、直った挙動を保証してくれません。テストが緑であることと、抽出器が正しく動いていることは別の主張です。今回の修正で、その当たり前の区別をもう一度コードに書き直すことになりました。断定語を数える計器自体が、数える対象を見落としていては意味がありません。抽出のロジックをどれだけ丁寧に書いても、その手前にある「どこが散文で、どこがコードなのか」の境界判定が甘ければ、下流の集計はすべて信用できなくなってしまいます。TSXとしての構文解析に委ねたことで、この境界判定は手書きの正規表現的な推測から、コンパイラが確定させた事実へと置き換わりました。
