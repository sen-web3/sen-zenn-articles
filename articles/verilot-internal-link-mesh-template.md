内部リンクとは、同一サイト内のページ同士を貼り合わせるハイパーリンクのことです。検索エンジンのクローラーが辿る経路を作ると同時に、関連するトピックが同じサイト内にまとまっていることを示す手がかりにもなります。個人開発でブログを書いていると、この内部リンクの整備は後回しになりがちです。私が運営しているVerilotのブログも例外ではありませんでした。

## きっかけは4本の記事のリンク状況を見直したこと

Verilotのブログには現在4本の記事があります。ある日ふと内部リンクの状態を棚卸ししてみたところ、次のような状態になっていました。

- 記事Aから記事Bへは貼ってあるが、BからAへは貼っていない（片方向のみ）
- 記事Dに至っては、他のどの記事からもリンクされていない（被リンクゼロ）

原因ははっきりしていて、記事を書くたびに「この話題は前の記事と関連しているな」と思ったらその都度本文にリンクを手動で足していたからです。新しい記事を書くときに、過去の記事のことをすべて覚えていて律儀にリンクを足す、という運用は個人開発では続きません。記事数が増えるほど抜けが増える設計になっていました。

## 本文編集ではなくテンプレート側で解決する

このとき考えた選択肢は2つでした。

1. 4本の記事のMarkdown本文を見直して、相互リンクになるよう手直しする
2. 記事ページのテンプレート側に「関連記事」セクションを機械的に追加し、本文には触れない

1は今ある4本の抜けを直すだけなら早いのですが、次に5本目を書いたときにまた同じ抜けが起きます。本文への手作業に依存している限り、記事数が増えるほど破綻するリスクは消えません。

そこで採用したのが2です。VerilotのブログはNext.jsのApp Routerで`app/blog/[slug]/page.tsx`が全記事を描画する共通テンプレートになっています。ここに「Related guides」セクションを追加し、その中身は本文編集ではなく`BLOG_POSTS`という記事一覧の配列から機械的に算出する形にしました。

```tsx
// app/blog/[slug]/page.tsx
const relatedPosts = BLOG_POSTS.filter((p) => p.slug !== post.slug);
```

やっていることは単純で、記事一覧から自分自身を除いた残り全部を関連記事として扱っているだけです。現時点で記事は4本しかないため、自分以外の3本は文脈的にも十分「関連」と呼べる規模感です。記事数がもっと増えたらタグやカテゴリでフィルタする実装に切り替える前提で、今はあえてシンプルにしています。過剰な設計をして動かさないより、今の記事数に見合ったコストで正しく動くほうを選びました。

## 静的生成との相性を確認する

Verilotのブログは全記事をビルド時に生成する完全静的なページです。`dynamicParams`を`false`にして、`generateStaticParams`で登録済みのslugだけをプリレンダーしています。

```tsx
export const dynamicParams = false;

export function generateStaticParams() {
  return BLOG_POSTS.map((post) => ({ slug: post.slug }));
}
```

Related guidesのリンク先も同じ`BLOG_POSTS`から生成されるため、リンク切れやビルド後の不整合が起きる余地がありません。記事を1本追加するときにやることは、`BLOG_POSTS`にエントリを1つ足してMarkdownファイルを置くことだけです。関連記事欄への追加や、既存記事からの被リンク付与は自動的に発生します。新しく書いた記事は初日からメッシュに組み込まれ、被リンクゼロの状態は構造上発生しなくなりました。

## JSON-LDと合わせてクロール経路を固める

Related guidesと同時に、各記事には`Article`型のJSON-LDも埋め込んでいます。

```tsx
const jsonLd = {
  "@context": "https://schema.org",
  "@type": "Article",
  headline: post.title,
  description: post.description,
  datePublished: post.datePublished,
  author: { "@type": "Organization", name: "Verilot" },
  publisher: { "@type": "Organization", name: "Verilot" },
};
```

構造化データは検索結果の見え方を整える役割が中心ですが、内部リンクとセットで整備すると効果が変わってきます。JSON-LDが各記事の意味づけをはっきりさせ、Related guidesがその記事同士を実際のリンクで繋ぐ。この2つが揃って初めて、クローラーがトピック単位で記事群を巡回しやすくなります。有料広告に頼らず検索経由の流入を増やしたい個人開発では、被リンクを外部から集める前に、まず自サイト内のリンク構造を破綻なく組んでおくことが土台になると考えています。

## 設計判断として残しておきたいこと

今回の対応ではっきりしたのは、内部リンクの抜けを見つけるたびに本文を直す運用は、記事数が少ないうちから早々にやめておくべきだったということです。テンプレート側に寄せておけば、次に書く記事のことを気にする必要がなくなります。書くべきは記事の内容だけで、リンク構造はテンプレートが保証してくれます。

今後記事数が増えてきたら、`relatedPosts`のフィルタ条件をタグやカテゴリ単位に拡張し、トピッククラスタをより明確に分ける予定です。ただしその変更もテンプレート側の一箇所を直すだけで済むはずで、この設計にしておいて良かったと感じています。個人開発のブログ運用では、こうした「後から気づいて焦って直す」を減らすために、最初からメンテナンスコストの低い場所にロジックを置いておくことが効いてくると実感しています。
