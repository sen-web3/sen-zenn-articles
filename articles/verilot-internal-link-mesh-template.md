# 個人開発ブログの内部リンク、本文編集に頼らずテンプレートで自動的に繋げる設計にした話

内部リンクとは、同一サイト内のページ同士をハイパーリンクで結ぶ仕組みのことです。クローラーの巡回経路を作り、関連する記事群を「トピッククラスタ」としてまとめて評価してもらうための土台になります。Verilotのブログをメンテナンスしていて、この内部リンクの抜けが記事間で放置されていたことに気づいたので、今回はその是正と再発防止の設計を記録しておきます。

## 見つかった問題

ブログの記事数はまだ4本しかありません。少ないからこそ全記事を相互にリンクさせるのは簡単なはずですが、実際に洗い出してみると片方向リンクしかない組み合わせがあり、さらに他のどの記事からもリンクされていない記事が1本ありました。原因は単純で、記事を書くたびに本文中で「関連記事」を手で追記していたからです。新しい記事を書いた時点では既存記事へのリンクを張れても、逆方向（既存記事から新記事へのリンク）を張り直す作業を毎回忘れていました。

本文編集で内部リンクを管理する限り、記事数が増えるほどこの抜け漏れは構造的に増えていきます。これは運用でカバーする話ではなく、テンプレート側で吸収すべき問題だと判断しました。

## なぜ本文編集をやめたか

このブログの記事ページには、もともと本文の扱いについてこういう前提があります。

```tsx
// Editor-approved markdown, rendered verbatim (body is never edited here).
// renderPostHtml only adds anchor ids to H2/H3 so the TOC can link into it.
const markdown = readPostMarkdown(post);
const html = renderPostHtml(markdown);
```

本文のMarkdownは「承認済みの原稿」として扱っていて、レンダリング時に加工するのはH2/H3への見出しID付与だけです。つまりこのページでは、本文に後から手を入れて内部リンクを差し込むという運用自体が設計と相性が悪いということです。だったら本文の外、テンプレート側に「関連記事」の枠を用意して、そこはコードが機械的に埋める方が理にかなっています。

## テンプレート側で埋める実装

記事一覧は`BLOG_POSTS`という配列で一元管理されているので、現在表示している記事以外を関連記事として抽出する処理は1行で済みます。

```tsx
const relatedPosts = BLOG_POSTS.filter((p) => p.slug !== post.slug);
```

今は記事が4本なので、これは実質「自分以外の全記事」を関連記事として出す実装です。過不足なく全記事が全記事にリンクする完全メッシュ構造になり、片方向リンクや被リンクゼロという状態がそもそも発生しなくなります。将来記事数が増えてきたら、タグやカテゴリでフィルタして件数を絞る判断が必要になりますが、それは記事数が実際に増えてから考えれば十分だと考えています。今の規模で複雑な関連度スコアリングを作り込むのは、投資として見合わないと判断しました。

ページ側は`export const dynamicParams = false;`で完全静的にビルドされるため、この`relatedPosts`の計算もリクエスト時ではなくビルド時に1回だけ走ります。

```tsx
export const dynamicParams = false;

export function generateStaticParams() {
  return BLOG_POSTS.map((post) => ({ slug: post.slug }));
}
```

ランタイムコストがゼロなので、関連記事の抽出ロジックを多少複雑にしても表示速度には影響しません。ここは安心して将来ロジックを足せるポイントです。

このセクションを「Related guides」という見出しでテンプレートの本文末尾に固定配置し、新しい記事を追加すると`BLOG_POSTS`にエントリが増えるだけで、既存記事からも新記事へのリンクが自動的に張られ、新記事からも既存記事へのリンクが自動的に張られます。記事を書く人間が内部リンクの往復を意識する必要がなくなりました。

## 構造化データ側も合わせて整備

内部リンクだけでなく、クローラーがサイト構造を理解するための情報も同時に見直しました。以前はArticleのJSON-LDが単体で発行元不明のOrganizationを指しているだけでしたが、パンくずリストとpublisherの`@id`参照を追加しています。

```tsx
// 2026-07-29 SEO/GEO pass: the page previously emitted a single Article
// block with an anonymous Organization. It now emits the publisher entity,
// a breadcrumb trail, the Article (with dateModified + author/publisher by
// @id), and — where the article has an FAQ section — a FA
```

内部リンクのメッシュとパンくずのJSON-LDは役割が違います。前者はクローラーが実際に辿る経路そのもの、後者はその経路が持つ階層関係の意味づけです。両方揃って初めて、トピッククラスタとしてまとまりを持った塊だとクローラーに伝わると考えています。

同じ「テンプレート側に寄せる」という方針は、OGP画像の生成でも踏襲しています。`generateMetadata`で静的な画像URLを固定指定すると、記事ごとに見出しを焼く`opengraph-image.tsx`のファイル規約が上書きされてしまい、実際に3日間すべての記事が同じOGカードになるという事故を起こしました。個別の記事ページで何かを上書き指定するのではなく、規約とテンプレートに判断を委ねる方が事故が減るという学びは、内部リンクの設計判断とも根っこは同じだと感じています。

## 結果

有料広告を使わずに検索流入を作るなら、サイト内にある資産（記事）同士をどれだけ密に、そして機械的に漏れなく繋げられるかがそのまま効いてきます。手動編集に頼った内部リンクは、書いた瞬間は正しくても記事が増えるたびに劣化していきます。テンプレート側で機械的に埋める設計にしたことで、これから何本記事を追加してもメッシュ構造が崩れる心配がなくなりました。
