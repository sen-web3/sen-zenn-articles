x402とは、HTTPの402 Payment Requiredステータスコードを使って、APIやリソースへのアクセスにオンチェーン決済を紐づけるプロトコルです。`@vet402/sdk` は、このx402決済をエージェントが自律的に実行する前に「本当に払って良い相手か」を判定してから署名に進むための、TypeScript製の関所（ゲート）です。中核にあるのが `payOrRefuse` という関数で、名前の通り「払う」か「拒否する」かの二択しか返しません。

この記事では、0.7.1で加えた「知らない判定語は拒否する」という規則と、それを支えるfail-closedの設計、そして支払いの記録（receipt）の形について、実装レベルで書きます。

## payOrRefuseはdenyを「返さない」

まず前提として、`payOrRefuse` には他の決済ガード実装（コード中では比較対象としてSpendGuardという名前を使っています）と大きく違う点が1つあります。一般的なガードはallow/denyを返り値として返し、実行は呼び出し側のウォレットスタックに委ねます。`payOrRefuse` はそうではありません。denyのとき、署名処理そのものにたどり着かない作りになっています。

```ts
/
 * 判定の流れ（5行）:
 *   1. 呼び出し側の誤り（0x でない payee 等）は throw。名前解決も判定取得もしない
 *   2. 呼び手が名乗った上限を、判定を引く前に当てる（price_above_ceiling）
 *   3. `GET /resources/{id}/decision?role=payer` を引く。読めない・degraded・ALLOW でない → 拒否
 *      3'. 404 not_found（カタログ外）→ 402 の payTo と受取人スコアだけで判定する
 *   4. 402 チャレンジを取り、payTo / network / asset / scheme / 金額を照合
 *   5. 全部通ったときだけ `./x402-pay.js` を動的 import して署名 → 売り手へ再送 → attest
 */
```

ポイントは、支払い実装（`x402-pay.js`）がALLOWのブランチの内側でしか動的importされないことです。denyのコードパスには、そもそも署名する手段が存在しません。これは「呼び出し側が判定結果を無視して払ってしまう」という事故を構造的に潰すための設計です。判定ロジックにバグがあっても、署名に届く経路が物理的に1本しかなければ、バグの影響範囲は限定できます。

## 起：知らない判定語が来たらどうなるか

0.7.1を書いているときに引っかかったのが、decisionの判定語（status）が将来増える可能性でした。現状はALLOW / degraded / not_foundといった語を想定していますが、カタログ側の実装が進めば、新しい状態を表す語が追加されるのは自然な流れです。例えば一時停止中を示す語や、審査待ちを示す語が後から生えてくるかもしれません。

ここで素朴に書くと、switch文のdefaultを「とりあえず通す」側に倒してしまいがちです。特に、呼び出し側が何らかの理由で特定のリソースやエラーコードを免除リストに入れている場合、「免除設定があるなら知らない語でも通してよいのでは」という判断は、実装としてはむしろ自然に出てきます。免除の仕組みを先に作っていたら、なおさらそう考えたくなります。

しかし判定語が増える理由は、たいていリスクが新しく見つかったときです。つまり「知らない語」は「安全が確認されていない語」であって、「安全とわかっている語」ではありません。ここを免除設定の有無で緩めてしまうと、判定サーバ側の仕様変更が、知らぬ間にクライアント側のガードを無効化することになります。

## 転：ALLOW以外は全部拒否、免除設定があっても拒否

そこで0.7.1では、判定語の扱いをallowlist方式に寄せました。コードのコメントにある通り、ステップ3は「ALLOWでない→拒否」であり、ALLOW以外のケースを列挙してdenyにするのではなく、ALLOWであることを唯一の通過条件にしています。degradedもnot_foundも、そして将来追加される未知の語も、すべて同じ扱い、つまり署名に届かない側に落ちます。

この方針の裏にあるのは、denyリストではなくallowリストで判断するという古典的なfail-closedの原則です。知らない語をdenyリストに追加し忘れることは起こり得ますが、ALLOWという1語だけを唯一の通過条件にしておけば、追加し忘れという事故自体が構造的に起きません。免除の設定は、カタログに存在しないリソース（404 not_found）を受取人アドレスのスコアだけで判定する、という別のステップ（3'）でのみ効くようにし、判定語そのものの意味を書き換える力は持たせていません。

さらに、このステップ5の手前でもう1つ詰まった箇所がありました。2026-09-05まで、このファイルは買い手側からfacilitatorのsettleエンドポイントを叩く形になっていました。しかしx402の設計では、決済を確定させるのは本来売り手側です。買い手からfacilitatorを呼ぶ形のままだと、09-08に予定していた実支払いのテストで、金は動かず、拒否された理由も記録に残らないところでした。

```ts
/
 * 5 について: 買い手は facilitator を呼ばない。決済するのは売り手（x402-pay.ts の
 * 冒頭に一次根拠）。2026-09-05 まで、ここは買い手から `x402.org/facilitator/settle` を
 * 叩いていた。その形のまま 09-08 に実支払いをすれば、金は動かず理由も残らなかった。
 */
```

修正は、署名後のフローを「売り手へ再送→attest」という形に作り直すことでした。買い手が自分で決済を確定させるのではなく、署名済みのauthorizationを売り手に送り返し、売り手がsettlementを行う。その結果をattestとして記録する、という順序にしています。これは単なるバグ修正ではなく、「誰が決済を確定させるか」という責務の置き場所をx402の仕様に合わせ直した変更です。

## receiptの形

ステップ4で照合しているのはpayTo / network / asset / scheme / amountの5項目です。これは呼び手が名乗った上限（ceiling）とも、実際に届いた402チャレンジの内容とも両方照合しています。ここで一致しなければ、やはり署名には届きません。

そしてステップ5の最後にあるattestが、支払いの記録を残す部分です。ALLOWだった判定、照合に使ったpayToや金額、署名後に売り手から返ってきたsettlementの結果までを一続きの記録として残すことで、「なぜ払ったのか」「払った結果どうなったのか」を後から追跡できる形にしています。拒否した場合も同様に、どのステップで止まったか（上限超過なのか、判定語がALLOWでなかったのか、照合が合わなかったのか）が記録に残ります。支払いの成功だけでなく、拒否の理由も同じ粒度で残すという点が、検証という仕事をする上では欠かせません。

## 結

判定語をdenyリストで管理せずALLOWだけを唯一の通過条件にしたこと、そして決済の確定を売り手側に委ねてattestという記録を必ず残す形にしたこと。この2つは別々の修正に見えて、実は同じ設計思想から出ています。知らないもの・確認できないものには権限を渡さず、渡した場合は必ず理由を記録する。vet402はこのfail-closedと記録の両輪があって初めて、エージェントの支払いを外部から検証できる機関として成立しています。
