x402とは、HTTPの402ステータスコードを使い、API呼び出しごとにオンチェーン決済を挟んでレスポンスを返すためのプロトコルです。支払いが通れば売り手は200 OKを返しますが、その本文の中身が実際に使える答えになっているかどうかは、決済の成否とは別の話です。vet402では「支払いが通って2xxで本文が返ってきた」ことを独立に観測していますが、その本文の一部は見た目こそJSONのオブジェクトなのに、中身はエラーメッセージやok:falseの失敗印、HTMLのエラーページ、空の箱だったりします。今回はこの「答えの形をしていない本文」を、文面の言葉ではなくJSONの構造だけで判定する純関数を書いた話をします。

## 起: 数えてみたら1.2%が答えの皮をかぶったエラーだった

vet402では観測した本文をそのまま保存しています。2026年10月15日時点で、直近30日分の5,729行を対象に本文の先頭を見てみたところ、約1.2%（68行・延べ24ホスト）が、支払いが通ったにもかかわらず答えの形をしていませんでした。`{"error":"missing 'symbol'"}`のような200の中のエラー文、`{"ok":false}`のような失敗フラグ、HTMLのエラーページ、`{"data":[]}`のような空の箱のどれかです。これは4つの型だけに絞って数えた値なので、実際にはもっと多い可能性があります。

この傾向は、外部のx402関連の開発者（@ziggydakid）からの指摘とも一致していました。「一番よく見るのは200の中のエラー文」という言葉で、自分が数字で確認した現象を裏付けてもらった形です。

問題は、この種の本文を「正しく届いた答え」として数に入れてしまうと、vet402が出す評価が実態より甘く見えてしまうことです。かといって、エラーの言葉が含まれているからといって機械的に弾くと、今度は正当な答えまで誤って弾いてしまいます。例えば`{"sandbox_id":"sb-1","status":"running","timeout_s":60}`は"timeout"という単語を含みますが、これはジョブの実行状況を正しく報告している本物の答えです。実際に言葉ベースの判定を試したところ、半分ほどが誤検出になりました。

## 転: 形だけで見分ける、控えめな4つの規則

そこで言葉を見るのをやめて、JSONの構造だけで判定する`answerShapeOf`という純関数を書きました。判定する型は4つに絞っています。

```typescript
export type AnswerShape = "error_object" | "error_flag" | "html_page" | "empty_structure";

const ERROR_KEYS = new Set(["error", "errors", "validationerrors", "err", "error_message", "errormessage"]);
const ERROR_COMPANION_KEYS = new Set([
  "code", "message", "status", "statuscode", "success", "ok",
  "detail", "details", "request_id", "requestid", "timestamp", "hint", "docs",
]);
const EMPTY_WRAPPER_KEYS = new Set(["data", "result", "results", "items"]);
```

`error_object`は、最上位のオブジェクトの鍵がエラーの鍵（`error`等）とその添え物（`code`や`message`等）だけで構成されている場合に限ります。ここで重要なのは、エラーの鍵の隣に中身のある他の鍵が1つでもあれば、答えの中身を持っているとみなしてerror_objectにはしない、という点です。例えばテストに書いた`{"price":84378.32,"symbol":"BTC","error":null}`は、エラーの鍵こそありますが`price`や`symbol`という実質的な答えが入っているため、判定はnullになります。`{"data":[1,2],"error":"partial"}`も同様です。これは「誤って正当な答えを拾わない側に倒す」という方針をそのままコードにしたものです。

`error_flag`は`ok:false`や`success:false`、`status:"error"|"fail"|"failed"`のような明示的な失敗の印を最上位に持つ場合です。`html_page`は本文の先頭が`<!doctype html`や`<html`で始まるかどうかだけを見ます。`empty_structure`は`{}`や`[]`、`null`、空文字、または`data`・`result`・`results`・`items`という鍵の値が空の配列・空のオブジェクト・nullだけのケースです。

テストで正答を誤判定しないことを確認した例がこちらです。

```typescript
assert.equal(answerShapeOf('{"url":"https://example.com","status":200,"responseTimeMs":275,"tls":{"valid":true}}', J), null);
assert.equal(answerShapeOf('{"results":[{"url":"https://onescales.com","statusCode":200,"isRedirect":false}]}', J), null);
assert.equal(answerShapeOf('{"sandbox_id":"sb-1","status":"running","timeout_s":60}', J), null);
```

1つ目はサイトのステータスを調べるAPIで、`status:200`という値そのものが答えの本体です。言葉だけを見て判定していたら、ここで誤って弾いていたはずです。構造を見る規則にしたことで、こうした「エラーっぽい語を含むが本物の答え」を素通りさせられるようになりました。

判定できないものはnullを返すように徹底しました。読めないJSON（`{"a":`のような壊れた本文）や、空文字、プレーンテキスト、数値や文字列だけの答え（`42`や`"BTC"`）は、この関数の担当外です。壊れたJSONの扱いは別の判定（unparseable）に任せ、この関数は「読み切れて、空でなく、2xxで返ってきた本文」だけを受け取る前提にしています。呼び出す側の責務を絞ることで、1つの関数が抱える判断を減らしました。

## 影の記録に留めた理由

この判定結果は`raw_response_meta.answerShape`というフィールドに記録するだけで、vet402が公開する評価（status・L2の判定・BLOCK等）には一切影響させていません。これには理由があります。200の中のエラーの多くは、実は売り手側ではなくvet402側の呼び出しミスで起きているからです。`missing agentId`のようなエラーは、こちらが宣言された入力パラメータを正しく送らなかった結果である可能性が高く、それをそのまま売り手の失点として扱うと冤罪になります。

これは2026年9月29日に起きたL2の冤罪34出品と同じ構図です。あのときは判定ロジックの不備で、実際には正常に機能していた出品を34件も誤ってブロック相当の評価にしてしまいました。その反省から、新しい判定を本番の評価に組み込む前には、数週間分のデータを溜めて傾向を確認し、どちらの側の失敗かを切り分ける規則を固めてから、独立したレビューを通すという手順を踏むようにしています。answerShapeOfはまだその途中段階にあり、今は観測のためだけに動いています。

実際、この観測を続けたことで、68行のうち大半がvet402側の呼び出しパラメータ不備に起因していることが分かってきました。売り手の落ち度として数えていたら埋めていたはずの冤罪を、公開前の段階で見つけられたことになります。これは小さな結果ですが、「確信が持てるまでは影の記録に留める」という手順が実際に機能した例だと受け止めています。

## 結

今回書いたのは、言葉を信じずに構造だけで判定するという小さな規則でしたが、根底にあるのは「確信が持てるまでは公開の評価に反映しない」という一貫した態度です。vet402は、新しい判定ロジックを追加するたびに、それがどちらの側の責任かを見極め切るまで影の記録に留め、誤って正当な答えを拾わない側に倒すという手順を崩さずに積み上げています。だからこそ、数字で示す評価の裏側に冤罪を抱え込まない設計になっていると考えています。
