eth_getLogs とは、EVM 系チェーンのノードに対して、指定したブロック範囲とアドレス・トピックの条件でイベントログを取得する JSON-RPC メソッドのことです。vet402 では x402 決済の履行を検証するために、オンチェーンの決済イベントをこのメソッドで読み直して索引を作っています。読み直しの対象期間が広がるほど、公開 RPC はこのメソッドに冷たくなっていきます。

## 起: 広い範囲を投げると断られる

vet402 の検証は、対象アドレスの決済ログを過去に遡って読み直すところから始まります。最初の実装は素朴で、fromBlock と toBlock をそのまま渡して一回の eth_getLogs で済ませていました。ローカルの短い範囲ではこれで問題なく動きます。問題は本番相当の長期バックフィルです。

Base の公開 RPC には eth_getLogs のブロック範囲に上限があり、超えた範囲を投げるとエラーで断られます。Alchemy の Base エンドポイントでもおおむね 2,000〜10,000 ブロック程度が目安で、これを超えるレンジクエリは拒否されるか、タイムアウトしてレスポンスが返ってきません。実際に 25 万ブロック相当の追いつき（catch-up）レンジを一発で投げたところ、RPC 側で弾かれるケースと、返ってきても極端に遅いケースの両方に遭遇しました。

さらに厄介だったのが、一部の実装で範囲外のクエリが黙って空配列を返してくることです。エラーにならず `[]` が返るので、呼び出し側は「その期間にはイベントがなかった」と誤認してしまいます。決済の履行を検証するサービスにとって、これは単なるバグではなく誤検証に直結する問題です。失敗を失敗として扱わない RPC 応答が一番厄介だと痛感しました。

## 転: 範囲を刻み、並列に投げ、失敗は失敗として扱う

対処の軸は三つです。ブロック範囲を一定サイズに刻むこと、刻んだチャンクを適度な並列度で投げること、そして 0 件という結果を鵜呑みにせず失敗条件を明示的に持つこと、という設計にしました。

まずチャンクサイズです。環境変数 `GET_LOGS_CHUNK_BLOCKS` で調整できるようにしつつ、デフォルトは保守的な 2,000 ブロックに固定しています。

```ts
export function getLogsChunkSize(): bigint {
  const raw = process.env.GET_LOGS_CHUNK_BLOCKS;
  if (!raw) return 2_000n;
  try {
    const size = BigInt(raw);
    return size > 0n ? size : 2_000n;
  } catch {
    return 2_000n;
  }
}
```

2,000 を既定値にしたのは、プロバイダの上限に対して余裕を持たせるためです。環境変数のパースに失敗した場合もサイレントに落とさず、安全側のデフォルトへフォールバックするようにしています。

次に並列度です。25 万ブロックを 2,000 ブロックずつ刻むと、約 125 回のラウンドトリップが発生します。インデクサが動くリージョンから RPC までの往復が 150〜300ms だとすると、これを完全に逐次実行した場合、1 回のバックフィルだけで 20〜40 秒がただの待ち時間として消えてしまいます。これがインデクサの追従コストを支配する最大の要因でした。

```ts
export function getLogsChunkConcurrency(): number {
  const raw = process.env.GET_LOGS_CHUNK_CONCURRENCY;
  if (!raw) return 4;
  const parsed = Number(raw);
  if (!Number.isFinite(parsed)) return 4;
  return Math.max(1, Math.min(8, Math.floor(parsed)));
}
```

固定の小さなファンアウト（デフォルト 4）を入れるだけで、待ち時間はほぼ線形に削減できます。値は 1〜8 にクランプしていて、1 にすれば旧来の完全逐次実行と同じ挙動に戻せます。プロバイダがレート制限を始めたら運用側でこの値を下げればよく、コード変更は不要です。コメントにも書いた通り、ここを二桁に上げることは意図的に禁じています。目的は Base のブロック生成速度に追いつくことであって、RPC を叩き潰すことではないからです。

チャンク間の待機も環境変数で持たせています。

```ts
function getLogsChunkDelayMs(): number {
  const raw = process.env.GET_LOGS_CHUNK_DELAY_MS;
  if (!raw) return 0;
  const parsed = Number(raw);
  return Number.isFinite(parsed) && parsed > 0 ? parsed : 0;
}
```

並列度・チャンクサイズ・遅延を別々の環境変数に分けているのは、プロバイダごとの制限が独立に変わるからです。レート制限に当たったときに並列度だけ下げたいケースと、1 リクエストあたりの範囲だけ狭めたいケースは別物なので、パラメータを混ぜずに分離しました。

もう一つ詰まったのが toBlock の解決です。タグとして `"safe"` や `"finalized"` が渡ってきたとき、最初の実装は雑に扱っていて意図しない範囲になっていました。

```ts
if (toBlock === "safe" || toBlock === "finalized") {
  // "safe"/"finalized" refer to the latest safe/finalized block, not
  // genesis — resolve the actual block number via the tag rather than
  // defaulting to 0n
  const block = await client.getBlock({ blockTag: toBlock });
  return block.number ?? (await client.getBlockNumber());
}
```

ここでのポイントは、タグの解決に失敗する経路でも 0n（ジェネシス）にフォールバックしないことです。もし誤って 0n を返すと、範囲がチェーン全体まで一気に広がり、本来小さく保ちたいチャンクが巨大化してしまいます。わずかな分岐の取り違えが、バックフィル全体の挙動を壊すことを示す例でした。

個々のチャンク取得には指数バックオフと範囲の二分割（bisection）を持たせています。範囲上限エラーを受けたら、同じ範囲をそのまま再試行するのではなく、範囲を半分にして投げ直し、それでも弾かれるならさらに半分にします。プロバイダ側の制限値を事前に正確には把握できない以上、実際に弾かれた応答から逆算して範囲を狭める方が確実だと考えました。同時に、このバックオフを使い切っても解決しない場合は、呼び出し元に「取得できなかった」という失敗を明示的に返す設計にしています。空配列を返して成功扱いにする経路は作っていません。索引が「イベントがなかった」のか「読めなかった」のかを区別できなければ、決済の有無を判定するサービスとして成立しないからです。

予備の RPC への切り替えも同じ思想の延長です。主系のエンドポイントが範囲エラーやタイムアウトを繰り返す場合、同じチャンク取得ロジックを予備のエンドポイントに対して再試行します。チャンクサイズ・並列度・バックオフの仕組みをそのまま使い回せるのは、取得経路をチャンク単位の小さな処理として独立させておいたからです。RPC を切り替えるために別のロジックを書く必要はありませんでした。

この一連の仕組みを入れてからは、25 万ブロック規模のバックフィルでも範囲エラーで処理全体が止まることがなくなり、プロバイダ側のレート制限に当たったときも環境変数の調整だけで復旧できるようになりました。実装を分岐ごとに見直す作業は地味でしたが、そのぶん「読めないときは読めないと言う」という最低限の約束を守れる形になったと思います。

## 結

決済ログの読み直しは、0 件という結果を安易に信用した瞬間に意味を失います。vet402 はブロック範囲を機械的に刻み、並列度とバックオフをプロバイダの制限に合わせて調整し、それでも読めなければ沈黙せず失敗として報告する、という一貫した設計で組んでいます。公開 RPC の都合に振り回されても検証結果の正しさだけは譲らないという方針が、この実装のすべての分岐に表れています。
